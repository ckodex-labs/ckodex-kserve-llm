# Operator release v0.20.0 upgrade runbook

This operational runbook provides step-by-step procedures for upgrading the CKodex KServe LLM Operator to release `v0.20.0` (commit `9da7f18`) with zero inference downtime.

## Overview of changes in v0.20.0

- Upgrades the default vLLM runtime engine to `v0.33.0` (PyTorch 2.14.0, CUDA 13.0).
- Introduces pure-domain Universal Tool Calling Protocol (UTCP v1.0.1) execution.
- Adds multimodal foundation model tasks (`ocr` for Baidu Unlimited-OCR-2, `segmentation` for Meta SAM 3).
- Updates LMCache integration to `v0.5.6` with shared memory prefix caching.
- Hardens Envoy Gateway 1.2.0 route fencing and automated security response headers.
- Normalizes container and pod field diffs (`L-OP-018`) to eliminate reconciliation drift loops.
- Enforces canonical chart structure in `deploy/helm` with byte parity verified by `hack/helm-contract` (`L-OP-013`).

## Pre-upgrade checklist

Before initiating the upgrade, complete these pre-flight checks:

1. **Kubernetes version compatibility**: Verify cluster is running Kubernetes v1.30 or higher:
   ```bash
   kubectl version
   ```
2. **GPU host driver verification**: If running GPU workloads, verify node drivers support CUDA 13.0 (driver version 580.178.04 or compatible):
   ```bash
   kubectl get nodes -l nvidia.com/gpu.present=true -o custom-columns=NAME:.metadata.name,DRIVER:.status.nodeInfo.kernelVersion
   ```
3. **Backup active custom resources**: Export snapshots of all active custom resources:
   ```bash
   mkdir -p /tmp/ckodex-backup-v019
   kubectl get llminferenceservices.serving.ckodex.com -A -o yaml > /tmp/ckodex-backup-v019/llminferenceservices.yaml
   kubectl get aipacks.serving.ckodex.com -A -o yaml > /tmp/ckodex-backup-v019/aipacks.yaml
   kubectl get agents.serving.ckodex.com -A -o yaml > /tmp/ckodex-backup-v019/agents.yaml
   kubectl get multimodalinferenceservices.serving.ckodex.com -A -o yaml > /tmp/ckodex-backup-v019/multimodal.yaml
   ```

## Step 1: Apply custom resource definitions

Apply the updated CRDs before rolling out controller manager binaries. The CRDs are backward compatible with all `v1` and `v1alpha2` workloads:

```bash
kubectl apply -f config/crd/serving.ckodex.com_llminferenceservices.yaml
kubectl apply -f config/crd/serving.ckodex.com_aipacks.yaml
kubectl apply -f config/crd/serving.ckodex.com_multimodalinferenceservices.yaml
kubectl apply -f config/crd/serving.ckodex.com_agents.yaml
kubectl apply -f config/crd/serving.ckodex.com_localmodelcaches.yaml
kubectl apply -f config/crd/serving.ckodex.com_modelservingprofiles.yaml
```

Verify that CRD definitions reflect version `v0.20.0`:

```bash
kubectl get crd llminferenceservices.serving.ckodex.com -o jsonpath='{.metadata.generation}'
```

## Step 2: Upgrade operator controller manager via Helm

Upgrade the operator using the canonical Helm chart in `deploy/helm`:

```bash
helm upgrade ckodex-operator deploy/helm \
  --namespace ckodex-system \
  --reuse-values \
  --set image.repository=ghcr.io/runbase-ai/ckodex-kserve-llm-operator \
  --set image.tag=v0.20.0
```

Monitor controller manager rollout status:

```bash
kubectl rollout status deployment/ckodex-operator-controller-manager -n ckodex-system --timeout=120s
```

Check operator manager logs for successful startup and leader election:

```bash
kubectl logs -n ckodex-system -l control-plane=controller-manager -c manager --tail=50
```

Confirm the log emits:
```text
{"level":"info","msg":"Starting controller-runtime manager","version":"v0.20.0","commit":"9da7f18"}
```

## Step 3: Validate workload reconciliation

The `v0.20.0` reconciler includes diff normalization (`L-OP-018`) in `internal/controller/reconciler/diff.go`. Existing deployments do not restart unless their specification was explicitly updated.

Verify that existing workloads remain running without pod restarts:

```bash
kubectl get pods -l app.kubernetes.io/managed-by=ckodex-operator -A
```

Inspect the operator metrics endpoint to confirm zero reconciliation error spikes:

```bash
kubectl exec -n ckodex-system deploy/ckodex-operator-controller-manager -c manager -- \
  curl -s http://localhost:8080/metrics | grep controller_runtime_reconcile_errors_total
```

## Step 4: Promote inference services to vLLM v0.33.0

To upgrade existing inference workloads to vLLM v0.33.0:

1. Update the workload image in the custom resource:
   ```yaml
   spec:
     template:
       spec:
         containers:
           - name: vllm
             image: vllm/vllm-openai:v0.33.0@sha256:d825baf9ce4b1b6bfc5ecc7b79880c7e6748c65a72d697ce3d47607aafa84c6e
   ```
2. Apply the updated manifest:
   ```bash
   kubectl apply -f my-workload.yaml
   ```
3. Observe rolling deployment:
   ```bash
   kubectl rollout status deployment/my-workload
   ```
4. Verify HTTP and health probes answer successfully:
   ```bash
   kubectl exec -it deploy/my-workload -c vllm -- curl -s http://localhost:8000/health
   ```

## Rollback procedure

If unrecoverable reconciliation or runtime failures occur during upgrade, follow these steps to roll back:

1. Roll back the Helm release to the prior revision:
   ```bash
   helm rollback ckodex-operator -n ckodex-system
   ```
2. Verify controller manager restored to prior version:
   ```bash
   kubectl rollout status deployment/ckodex-operator-controller-manager -n ckodex-system
   ```
3. If CRD schema conflicts occur, restore CRD definitions from pre-upgrade backup:
   ```bash
   kubectl apply -f /tmp/ckodex-backup-v019/
   ```
4. Check operator events and metrics for steady-state resumption:
   ```bash
   kubectl get events -n ckodex-system --sort-by=.lastTimestamp
   ```
